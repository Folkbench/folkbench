> **들어가며**: AI 애플리케이션을 프로덕션 환경에 올리는 과정에서 API 중계 서비스는 대부분의 개발자가 피해 갈 수 없는 관문입니다. 그런데 중계 서비스 공식 사이트에 걸린 “99.9% 초고속·안정”, “전용 고동시성 채널” 같은 홍보 문구를 믿고 막상 연결해 보면, 생각보다 훨씬 깊은 수렁이라는 사실을 깨닫게 됩니다. 오늘은 저희 팀이 “감으로 무작정 구매하던” 단계에서 “자동화 모니터링을 구축한” 단계에 이르기까지 겪은 쓰라린 경험을 이야기하고, 결제나 연동 전에 중계 서비스의 실체를 확인하는 테스트 프레임워크를 모두 공개합니다.

## 1. 그동안 AI 중계 서비스에 당했던 쓰라린 기억

솔직히 말하면, 오늘 이렇게 다차원 테스트 체계를 정리할 수 있게 된 것은 저희가 처음부터 똑똑했기 때문이 결코 아닙니다. 실제 돈과 프로덕션 장애, 사용자들의 불만을 대가로 치르며 몸으로 깨우친 결과입니다.

### 1. 함정 1: “가짜 200 OK”와 “조용한 끊김”

자동화 평가를 막 시작했을 무렵, 저희의 발상은 아주 단순했습니다. Python 스크립트를 하나 짜서 5분마다 중계 서비스에 POST 요청을 보내고, HTTP `200` 상태 코드와 텍스트만 돌아오면 조용히 체크 표시를 하며 서비스가 꽤 안정적이라고 여겼습니다.

그런데 프로덕션에 에이전트를 배포한 지 이틀도 채 되지 않아 고객 지원 쪽이 발칵 뒤집혔습니다. AI가 말하다가 갑자기 뚝 끊긴다, 생성된 내용의 논리가 완전히 엉망이다, 하는 사용자들의 호소가 곳곳에서 쏟아졌습니다.

로그를 뒤져 보면서 **정말 기가 막혔습니다!** 일부 중계 서비스는 업스트림 계정 풀이 바닥난 상황(429 속도 제한이나 401 인증 실패 등), 게이트웨이 타임아웃(504), 노드 장애를 감추기 위해 HTTP 프로토콜 계층에서는 버젓이 `200 OK`를 돌려주고 있었습니다. 더 기막힌 수법도 있었습니다. 스트리밍(SSE) 전송 도중에 뒤에서 몰래 `data: [DONE]`을 끼워 넣어 강제로 끝내 버리거나, JSON 안에 `{"error": "rate limit exceeded"}` 같은 문장을 그럴듯하게 넣어 모델의 답변인 것처럼 꾸몄습니다. 상태 코드만 보던 저희의 초기 “단순 무식한” 모니터링은 이런 “가짜 200”에 완전히 농락당한 셈입니다.

### 2. 함정 2: 야간의 “유령 지연”과 폭증하는 첫 토큰 지연 시간

한 번 당하고 나서 저희는 서둘러 개선에 나섰고, 24시간 정기 점검 모니터링을 추가했습니다. 낮에 측정하면 평균 응답 시간이 2초 안팎으로 유지되어 수치상으로는 아주 보기 좋았습니다. 하지만 밤 피크 시간대만 되면 프로덕션 시스템의 호출 타임아웃 비율과 사용자 이탈률이 로켓처럼 치솟을 줄은 누구도 몰랐습니다.

나중에 알고 보니, 대부분의 중계 서비스 백엔드에는 애초에 공식 직결 채널 같은 것이 없었습니다. 미국 리전 계정 풀이나 여러 지역의 프록시 노드를 잔뜩 섞어 연결해 둔 구조였습니다. 북미 업무 시간이나 중국의 야간 피크 시간대가 되어 동시 요청이 늘어나면 완전히 뻗어 버렸습니다. **가장 어이없었던 것은, 전체 답변을 생성하는 총 소요 시간은 여전히 4초 안팎으로 보였는데 첫 토큰(TTFT)이 나오기까지는 무려 12초가 걸렸다는 점입니다!** 프런트엔드에서 빈 입력 상자를 바라보며 10여 초를 멍하니 기다려야 한다면 누가 견딜 수 있겠습니까? 대부분의 사용자는 진작 참지 못하고 페이지를 닫아 버렸습니다.

이 두 번의 장애로 저희는 완전히 정신이 번쩍 들었습니다. **Ping 한 번, 요청 두어 개를 대충 보내 보는 수준의 확인은 복잡한 AI 프로토콜과 스트리밍 전송 앞에서는 그저 눈 가리고 아웅일 뿐입니다.**

## 2. “맹신”에서 “철저한 방어”로: 테스트 체계의 세 차례 진화

중계 서비스 업체의 마케팅 말잔치에 휘둘리지 않기 위해, 저희의 평가 방법론은 세 단계를 거쳤습니다.

### 1.0 시대: 블라인드 테스트와 감(경험주의)

- **방법**: Web UI에서 직접 프롬프트 몇 개를 보내 보거나, 요청 10번을 보내는 스크립트를 손으로 짜서 속도가 빠른지, 답변 품질이 좋은지 살펴봤습니다.
- **한계**: 테스트 샘플이 너무 작고 무작위성이 커서 완전히 운에 맡기는 셈이었습니다. 프로덕션 환경에서 높은 동시 요청이나 간헐적인 연결 끊김을 만나면 바로 문제가 드러났습니다.

### 2.0 시대: 동시 요청과 HTTP 상태 코드 모니터링(대략적인 모니터링)

- **방법**: Postman과 Locust로 다중 동시 부하 테스트를 돌리고, HTTP 상태 코드 분포, 평균 응답 시간, 성공률을 보기 시작했습니다.
- **한계**: 가장 바깥쪽 “게이트웨이”의 동작만 보일 뿐, 스트림 끊김, 위조된 오류, 토큰 출력 버벅임처럼 깊숙이 숨은 문제는 전혀 잡아내지 못했습니다.

### 3.0 시대: 스트리밍 상태 머신과 다른 업계의 노하우(정밀 관측)

자체 모니터링 지표가 한계에 부딪혔을 무렵, 저희는 초단타 매매(HFT)와 CDN 운영 분야에서 일하는 저우 형을 찾아가 이야기를 나눴습니다.

저우 형은 저희의 고민을 듣더니 핵심을 단번에 짚었습니다. **“AI API 중계 서비스를 평범한 Web API처럼 테스트하면 처음부터 방향이 어긋난 겁니다. 이건 본질적으로 장시간 연결과 높은 동시성을 지닌 네트워크 중간 노드입니다!”**

저우 형은 AI의 SSE 스트리밍 전송이 하위 토폴로지와 패킷 손실에 대한 민감도 면에서 **오디오·비디오 실시간 통신(WebRTC/RTMP)**, 그리고 **증권 시세 푸시**와 매우 비슷하다고 짚어 주었습니다. 전통적인 Web 계측 방식을 그대로 가져다 쓸 수는 없고, 초단타 매매에서 “Tick-to-Trade 초저지연”을 측정하는 방식과 CDN에서 “첫 프레임 로딩”을 다루는 구간 분리 방식을 참고해야 한다는 것이었습니다.

이 말에 자극을 받아 저희는 기존 모니터링 로직을 완전히 갈아엎고 다중 리전 분산 프로브를 구축했습니다. 네트워크 연결 수립, TLS 핸드셰이크, 첫 토큰 도착, 토큰 처리 속도, SSE 패킷 파싱을 모두 따로 분해해 측정하고, 여기에 통계 알고리즘을 더해 평활화 처리를 합니다. 이 방식이 바로 저희가 지금 사용하는 자동화 테스트 표준입니다.

## 3. 핵심 테스트 지표: 프로덕션 경험을 좌우하는 3대 차원

저우 형이 준 아이디어와 저희가 직접 겪은 시행착오를 바탕으로, 지금은 API 중계 서비스를 평가할 때 다음 3가지 핵심 차원의 다중 지표 매트릭스를 일률적으로 봅니다.

```text
                         ┌── TTFT(첫 토큰 지연 시간) -> 사용자가 느끼는 “기다림”
              ┌── 지연 ──┼── TPS(생성 속도) -> “타자기” 출력의 매끄러움
              │          └── P95/P99 지연 시간 -> 최악의 경우와 피크 시간대 성능
              │
테스트 지표 ──┼── 신뢰성 ──┬── 파싱 성공률 -> 가짜 200·비정상 형식 응답 걸러내기
              │            └── Retry-to-Success -> 지수 백오프 재시도의 장애 허용도
              │
              └── 스트림 품질 ──┬── 스트림 중단율 -> “말하다 끊기는지” 판정
                                └── 토큰 지터 -> 출력이 버벅이는지 평가
```

### 1. 지연 시간: “기다림”과 “생성”을 나눠서 본다

- **TTFT (Time to First Token)**: HTTP 요청을 보낸 시점부터 첫 번째 SSE 패킷을 받을 때까지의 밀리초입니다. 저우 형이 말한 “첫 프레임 소요 시간”에 해당하며, 기다리는 동안 사용자가 느끼는 초조함을 직접 좌우합니다. **프로덕션 환경의 필수 기준은 TTFT < 1.5초입니다.**
- **TPS (Tokens per Second)**: 첫 토큰이 나온 뒤의 지속 생성 속도(생성 토큰 수 / 지속 시간)입니다. TPS가 너무 낮으면 프런트엔드의 “타자기” 효과가 경운기처럼 덜컹덜컹 끊기게 됩니다.
- **P95 / P99 지연 시간**: 눈속임용 “산술 평균”은 믿지 마세요! 저희는 95번째와 99번째 백분위수의 응답 시간만 봅니다. 피크 시간대, 긴 컨텍스트, 채널 혼잡 상황에서 중계 서비스가 보여 주는 “진짜 참상”은 P95/P99 앞에서 곧바로 정체를 드러냅니다.

### 2. 신뢰성: “가짜 성공”을 꿰뚫어 본다

- **파싱 성공률(Parse Success)**: 요청이 `200`을 반환하는 것만으로는 부족합니다. 반환된 데이터 패킷을 공식 SDK가 정상적으로 파싱할 수 있어야 하고, 완전한 JSON 구조를 갖춰야 하며, 중계 서비스가 임의로 끼워 넣은 오류 메시지가 섞여서는 절대 안 됩니다.
- **재시도 성공률(Retry-to-Success Rate)**: 프로덕션 환경의 지수 백오프 재시도 메커니즘을 시뮬레이션해, 중계 서비스가 간헐적으로 429나 5xx를 반환한 뒤 3회 이내의 재시도에서 예비 채널로 전환해 빠르게 복구하는지 확인합니다.

### 3. 스트림 품질: “조용한 장애”를 잡아낸다

- **스트림 중단율(Stream Interruption)**: 공식 규약의 종료 표시인 `data: [DONE]`을 받기 전에 TCP 연결이 먼저 끊기거나 아무 응답 없이 멈춰 버리는 비율입니다.
- **토큰 지터(Inter-Token Jitter)**: 오디오·비디오 전송의 “네트워크 지터” 개념을 그대로 빌려 온 지표로, 인접한 두 SSE 패킷의 도착 시간 차이의 표준편차를 계산합니다. 지터가 지나치게 높으면 중계 서비스 백엔드 채널의 부하가 극도로 불안정하거나, 몰래 여러 겹의 프록시 버퍼링(Buffering)을 덧대 놓았다는 뜻입니다.

## 4. 이론과 업계 참고 자료: 혼자 만든 기준이 아닙니다

테스트 데이터를 더 객관적이고 설득력 있게 만들기 위해, 저희는 평가 로직을 세울 때 업계의 대표적인 운영·통계 표준 몇 가지를 참고했습니다.

### 1. Google SRE 운영 백서(The Four Golden Signals)

Google SRE(사이트 신뢰성 엔지니어링)는 **지연 시간(Latency), 트래픽(Traffic), 오류(Errors), 포화도(Saturation)** 네 가지를 4대 골든 시그널로 정리했습니다. 저희는 프로브 계측을 설계할 때 중계 서비스를 전혀 신뢰할 수 없는 외부 서비스로 간주하고, 모든 알림을 이 4대 골든 시그널을 중심으로 잡습니다.

### 2. OpenTelemetry 관측 표준과 W3C SSE 규격

스트리밍 응답에 대해서는 OpenTelemetry의 장시간 연결 Trace 계측 규격과 W3C의 Server-Sent Events 프로토콜을 참고해, 하위 프로토콜 계층에서 전 과정을 계측합니다. TCP 핸드셰이크, TLS 협상, Headers 수신, First Data Chunk 출력부터 `[DONE]` 신호까지 모두 기록합니다.

### 3. 윌슨 신뢰 구간 알고리즘(Wilson Score Interval)

중계 서비스의 안정성 순위를 매길 때 단순히 “성공 횟수 ÷ 전체 횟수”를 쓰면 사실 매우 불공평합니다. 예를 들어 10번 테스트해 모두 성공한 서비스(성공률 100%)가 10,000번 중 9,900번 성공한 서비스(성공률 99%)보다 통계적으로 반드시 더 믿을 만하다고 할 수는 없습니다.

소표본 편향을 해결하기 위해 저희는 **윌슨 신뢰 구간의 하한**을 점수 산정 근거로 도입했습니다.

```text
Score = (p̂ + z²/(2n) - z × √(p̂(1-p̂)/n + z²/(4n²))) / (1 + z²/n)
```

*(p̂: 실제 관측된 성공률, n: 전체 샘플 수, z: 95% 신뢰 수준에서의 정규분포 분위수)*

이 알고리즘을 도입한 뒤로는 샘플 수가 적거나 테스트 기간이 짧은 중계 서비스가 자동으로 감점되어, 순위의 신뢰도가 자연스럽게 훨씬 높아졌습니다.

## 5. 자동 모니터링 아키텍처: 프로브는 어떻게 작동할까

실제 아키텍처에서는 단일 머신에서 스크립트를 돌리는 방식을 버리고, 여러 노드가 협업하는 프로브 시스템을 구축했습니다.

```text
[다중 리전 프로브(AWS 미국 서부 / GCP 동아시아 / 유럽)]
       │
       ├──> [정기·버스트 동시 트래픽 생성기] ──> [중계 서비스 API 프록시 계층] ──> [업스트림 API / 계정 풀]
       │                                             │
       └──< [SSE 프로토콜 파서 & 상태 머신] <────────┘
               │
               ├──> [TimescaleDB / Prometheus(마이크로초 단위 지표 저장)]
               └──> [신뢰 구간 점수 & 이상 원인 자동 분류 엔진]
```

### 1. 분산 프로브 배치

AWS 미국 서부, GCP 동아시아(홍콩/도쿄), 유럽 노드에 경량 프로브를 배치했습니다. 여러 지역에서 동시에 요청을 보내면 지연이나 오류의 원인이 중계 서비스 자체 프록시 노드의 정체인지, OpenAI/Anthropic 공식 서비스의 변동인지 한눈에 구분할 수 있습니다.

### 2. 저수준 Socket 상태 머신

프로브는 요청을 보낸 뒤 Socket 상태 머신을 켜고 프레임 단위로 계측합니다.

- `CONNECTING`: 요청 발송 시각 t0 기록
- `FIRST_BYTE`: 첫 SSE Chunk 수신, TTFT = t1 - t0 기록
- `STREAMING`: Chunk 도착 간격, TPS, 지터(Jitter) 실시간 계산
- `COMPLETED`: 데이터 패킷의 정상 종료, `[DONE]` 표시 존재, JSON 구조의 유효성 검증

### 3. 이상 원인 자동 분류

프로브가 이상 오류를 포착하면 원인 분류 엔진이 자동으로 분류합니다.

- **게이트웨이 장애**: `502 Bad Gateway` / `504 Gateway Timeout` 반환 ──> 중계 서비스 자체의 Nginx/Envoy 노드가 다운된 것으로 판정합니다.
- **계정 풀 고갈**: `429 Too Many Requests` / `401 Unauthorized` 반환 ──> 중계 서비스의 다운스트림 동시성 제어가 부실하거나, 업스트림 키 잔액이 바닥난 것으로 판정합니다.
- **미들웨어 문제**: `200 OK`를 반환했지만 전송 도중 끊기거나 파싱에 실패 ──> 중계 서비스가 직접 만든 과금/프롬프트 차단 미들웨어의 버퍼 오버플로로 판정합니다.

## 6. 중계 서비스 선택에 관한 솔직한 조언과 함정 피하기 요약

지금 중계 서비스를 찾고 있다면, 다음 3가지 원칙만은 꼭 기억하세요.

1. **한 번의 테스트를 믿지 마세요**: 반드시 낮과 밤에 걸쳐 최소 3~7일 동안 연속으로 샘플링하고, 특히 야간 피크 시간대(21:00~01:00)의 P95 지연 시간과 성공률을 중점적으로 보세요.
2. **테스트에서는 반드시 스트리밍(Stream)을 켜세요**: 비스트리밍 요청은 지극히 위선적이어서 첫 토큰 지연, 미들웨어 버퍼링으로 인한 끊김, 중간 스트림 단절 같은 큰 함정을 모두 가려 버립니다.
3. **세상에 공짜 점심은 없습니다**: 터무니없이 싼 중계 서비스 뒤에는 공유 계정 풀이나 품질 낮은 프록시 노드가 있을 가능성이 크고, 심지어 저렴한 오픈소스 모델을 껍데기만 바꿔 Opus나 GPT-4o로 속이는 경우도 있습니다.
